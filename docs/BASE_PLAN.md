# サウンド単行本 ベース（雛形）化 棚卸しと計画

作成：2026-10-29（対象：v1.7.0 時点の sound-novel-single『空の郵便が届くまで』）
目的：このアプリを今後のサウンド単行本の標準ベースにするため、本固有の埋没箇所を洗い出し、集約と量産化の計画を立てる。本文書は棚卸しと計画のみで、実装の作り替えは含まない。

---

## 1. 全体像（現行の構成）

アプリは pwa-template 由来の Vite + TypeScript + vite-plugin-pwa 構成で、本の内容はほぼ `public/book/data.json` 駆動。制作側は Python の著作用パイプライン（`work/`、`data/`）で、アプリのビルドとは分離している（CLAUDE.md 記載どおり）。

- アプリ本体：`src/`（reader.ts 1,316行が中心、logic.ts、sound.ts、bgm-song.ts、storage.ts、debug.ts、install.ts、pwa.ts、main.ts）＋ `index.html`（210行）＋ `src/style.css`（633行）
- 本のデータ：`manuscript/story.md` → `work/build_data.py` → `data/chapters.json` ＝ `public/book/data.json`（同一内容を2か所に書く）
- 音声：`audio/ch1〜7.mp3`（章ごと）＋ 扉読み上げ用 `ch*-title.mp3`（作業中）→ `public/book/audio/` にコピー
- 絵：`public/book/cover.svg`（表紙・手描き）、`public/book/bg/ch1〜7.svg`（章背景線画・手描き）
- 音楽：音ファイルを持たず、`src/bgm-song.ts` の作曲データを Web Audio で合成再生
- 公開：`npm run build` の `dist/` を gh-pages ブランチへ**手作業で**反映（GitHub Actions はテストのみ）

良い土台である点：本文・ルビ・読み上げ文・章メタ情報は既に data.json に集約され、アプリはそれを描くだけになっている。テストも data 駆動の検証（tests/data.test.ts）と E2E（e2e/app.spec.ts、888行）が揃っている。ベース化は「ゼロから」ではなく「残りの埋没分の回収」が中心になる。

### 3.2 寄せられるもの（データ化だけで済む）

- 書名・著者・表紙の行割り・形式名・版表記（#1,2,3,4）→ ビルド時に index.html と manifest へ注入する形にすれば、直書きは消える
- 奥付の全文（#3）：書名・著者・朗読クレジット（narrators から自動生成）・形式・版表記から**自動生成**できる。朗読クレジットは声設定と二重管理にしない
- テーマ色（#1,8）：CSS変数へ注入
- 章の背景SVGとアニメーション種別（#6）：アニメーションは「rain / motes / glow / sunset / sway / cloud」等の**プリセット名で選ぶ**形にすれば、reader.ts の switch は章番号ではなくデータの `anim` 値で引ける
- 語り手の対応（#13）：原稿見出しの（名前）だけでは決めず、設定側で narrator を明示する
- 章見出しの解析（#12）：「第N章」の N は漢数字・算用数字・任意の章ラベルに対応させる

### 3.3 寄せられないもの（コード変更が要るもの）

- 表紙アートと章背景線画そのもの：本ごとの手描きが前提。ただし「型」の選択肢は用意できる（地色＋枠＋モチーフ部品の組み合わせ生成）。割り切りとして、**表紙は型＋差し替え可能**、章背景は「線画なし（無地＋アニメーションのみ）でも成立する」設計にしておくと量産時の詰まりが消える
- BGMの作曲データ（#5）：「デフォルトのバラード1曲を形式共通にする」か「本ごとに差し替える」かの方針決めが先。コード的には bgm-song.ts を差し替え可能なモジュールにするだけ
- 旧保存キーの移行処理（#9）：雛形からは外し、移行が要る本だけが持つ
- テストの本固有アサーション（#11）：設定ファイルから期待値を読む形に直す

| 段 | 現在の担い手 | 状態 |

| ビルド・検証 | `npm run verify`（lint/単体/build/check:dist）、E2E、CI（GitHub Actions） | 固定済み。良好 |
| 公開 | gh-pages へ**手作業**で dist を反映 | 手順は README 記載。自動化はされていない（事故防止には現状維持も選択肢） |

固定化の要点は2つ。(1) 生成・検証スクリプトを「声プロファイル（声ID・速度・スタイル・後処理）を設定で渡す1本」に統合すること。(2) 読み精査の段取り（辞書の作り方→全件照合→食い違いの統合判断→再生成→文字起こし照合）を**手順書として1枚に書く**こと。精査そのものは自動化しきれない（文脈判断が本体）が、手順が固定されれば冊ごとの品質が均一になる。

## 5. 仕様の固定点（「サウンド単行本 標準仕様」目次案）

この本で決まった作法を、形式の仕様として項目化する。仕様書は以下の章立てを想定。

1. **本の構造**：表紙 → 目次ページ → 章扉 → 本文ページ… → 最終ページ（「おわり」）→ 奥付ページ（独立）。戻り方向は本文→扉→目次→表紙までページ送りで辿れる
2. **表紙画面**：常時表示は表紙・再開ボタン（しおりがあるときだけ）・設定入口・下部中央の版数（デバッグ入口兼用）だけ
3. **読書画面**：操作UIは普段非表示、中央タップで表示（約3.5秒で自動消去）。常時表示はノンブルと下端の進捗ラインのみ。画面上の操作は再生/停止と設定入口だけ（章移動・シーク・表紙へ戻るは他手段で到達可能に保つ）
4. **ページと音声の追従**：ページが主、音声が従。めくれば朗読はそのページ先頭の文へ移る（連打時は260msデバウンスで最終ページへ1回）。音声→ページは前方向のみ、手動直後12秒は干渉しない。自動で進むのは再生中に朗読が次ページへ差しかかったとき・章の終了時だけ
5. **表示方式**：ページ形式（既定）／カラオケ方式（朗読位置より後の文は見せず場所だけ確保、文単位で現れる）。位置・しおりは方式をまたいで保持
6. **文の強調**：朗読中の一文だけを薄く強調（設定で切替可、既定オン）
7. **安全領域と枠**：枠の余白は safe-area-inset 連動の共通変数。進捗ラインは綴じ方向に連動（縦書き＝右→左）
8. **章扉**：章番号・タイトル・語り手名をかたまりで中央配置。「語り・」表記は使わない。扉は読み上げ対象（章題コール→本文）
9. **目次ページ**：本の1ページとして独立。列は枠いっぱいに広げず余白を残す。章が増えたら複数ページに分かれて送れること
10. **終わり方**：「おわり」は最終ページの本文の流れの末尾に独立した列で中央。奥付は別ページ（書名・著者・朗読/音楽クレジット・形式・版）
11. **設定項目**（設定集約・音／表示グループ）：再生速度、BGM、バックグラウンド再生、フリガナ、文の強調、背景イメージ、画面を暗くしない（Wake Lock）。記録のバックアップは置かない（形式の判断として固定）
12. **音まわり**：BGMは朗読比 約−7dB を目安、ビブラート/トレモロ/スウィングなし。Media Session 対応（章移動・±10秒）。バックグラウンド再生は設定で切替
13. **データ形式**：data.json のスキーマ（title/author/direction/totalChars/chapters[]）、章音声は章ごと1ファイル、文単位の位置情報が追従の正
14. **制作基準**：朗読テンポは完成音声で300字/分、読みは辞書で固定し全件精査、生成音声は全数文字起こし検証してから公開

## 6. 容量・配信

実測（v1.7.0 の dist）：

- 音声：`public/book/audio/` 合計 **約27MB**（章MP3×7、各3.5〜4.7MB、96kbps）。＋扉コール7ファイル（各35〜84KB、軽微）
- アプリ全体の dist も約27MB（大半が音声）。data.json は本文＋ルビ＋spoken を含み、音声に比べれば小さい
- 現行は workbox の precache で**全ファイルを初回に一括取得**（`globPatterns` に mp3 を含み、上限を5MBに引き上げ済み）。初回表示で約27MBを落とす設計で、冊が増える・章が長い本では線形に重くなる

> **v1.13.0 での決定（2026-10-30）**：一括取得の方式は**維持**する（分割・遅延取得にはしない。ユーザーが「シンプルさ」を優先して決定）。代わりに、(1) 朗読音声をモノラル 64kbps 化して総量を約17.3MB（20,000字換算で約33MB）まで圧縮、(2) precache 上限を 12MB に引き上げ、(3) 初回に総容量と Wi-Fi 推奨の案内を出す、の3点で重さに対処した。以下の遅延取得の検討は、方式を変える場合の参考として残す。

章ごとの遅延取得に変える場合の影響：

- 初回はアプリ本体＋第1章（＋表紙・データ）だけにでき、初期取得は数MBに圧縮できる
- 代償：(1) オフライン保証の意味が変わる（未取得の章は圏外で開けない。「全章ダウンロード済み」表示や、Wi-Fi時の事前取得ボタン等の代替が要る）(2) Service Worker のキャッシュ戦略を precache→runtime caching に組み替える必要があり、更新バナーや起動復旧の既存仕組みとの整合テストが要る (3) 受託納品では「届いた時点で全部入っている」方が説明が簡単、という商品面の判断もある
- 結論としては、**ベース化の初期段階では現行の一括方式を標準とし、遅延取得は「長い本向けの選択肢」として後段で入れる**のが安全。少なくとも容量の上限目安（例：1冊30MBまで）を仕様に置く

## 7. ベース化の作業計画

進め方の原則：**公開中の『空の郵便が届くまで』を壊さない**。アプリ本体は既に data 駆動なので、ベース化は「この本のリポジトリを雛形化する」のではなく、「雛形リポジトリを別に切り、この本はその最初の利用例として追随させる」二段構えが安全。

### フェーズ0：仕様と設定の固定（文書・設計のみ）
- 本書の内容を土台に「標準仕様書」と「book.config スキーマ」を確定
- BGM方針（共通曲か本ごと差し替え可）と表紙の型の方針を決める
- 規模感：小（文書中心）

### フェーズ1：設定の集約（この本のリポジトリ内で実施し、公開版で検証）
- index.html・vite.config.ts の書名/著者/奥付/色を設定ファイル経由に置換（注入の仕組みを入れる）
- reader.ts の章アニメーションをデータの `anim` プリセット参照に変更
